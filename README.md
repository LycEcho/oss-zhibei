# 开源选型 · 先懂类型，再选项目

> AI 起草、人工核验的开源项目选型导航。每个开源类型一篇「选型意见」：**默认选谁、什么情况换、不适合谁**。
> 不按编程语言分，按「一次选型决策里会放在一起比的那一组」分——因为 AI 时代，语言不是边界，用途才是。

---

## 这是什么

找开源项目不难，难的是「敢不敢用」：还活着吗？协议能商用吗？跟另外五个差不多的比该选谁？
本项目不罗列项目——每个类型先讲清楚「这是什么、怎么选」，默认推荐一句话给答案，全部判断挂证据和日期。

三条内容铁律：

1. **判断永远由人背书**——AI 只起草和供证据，每页盖「核验戳」：谁核验的、什么时候、依据什么
2. **不写正确的废话**——「各有优劣看场景」出现即返工；写不出「默认选谁」就照实说（见新星观察区）
3. **负面空间也是内容**——停更警示区、闭源对照项、边界物种裁决，都在页面上

## 怎么加一个类型（GitHub 就是数据库）

界面是引擎，内容全在 `data/types/` 里。**加类型不需要碰任何界面代码**：

1. 在 `data/types/` 下新建一个 `.js` 文件（比如 `my-new-type.js`），照抄现有文件的结构
2. 把文件路径加进 `data/types.js` 的清单数组里（顺序 = 首页卡片顺序）
3. 提交到 GitHub —— 页面自动出现新类型，搜索自动索引到里面的所有项目

更新某个类型的内容同理：只改它自己的文件，提交即生效。

### 数据字段说明

```js
window.TYPE_DATA.push({
  id: "my-type",              // 必填 · 唯一英文标识（用于页面路由）
  name: "类型名",              // 必填 · 中文显示名
  kw: "关键词1 关键词2",        // 必填 · 搜索关键词（空格分隔，用户搜这些词能找到本页）
  one: "一句话说明",           // 必填 · 首页卡片与页首的简介
  date: "2026-10-20",         // 必填 · 核验日期（数据是哪天抓的）
  src: "发现来源",             // 必填 · 如「四层漏斗 · 双圈交叉」
  status: "ok",               // 必填 · "ok"=有默认推荐 / "obs"=观察中
  count: 11,                  // 必填 · 已采集项目数（首页徽章显示）
  fit: ["适合谁1", ...],       // 推荐 · 适合的场景
  nofit: ["不适合谁1", ...],   // 推荐 · 不适合的场景（禁写套话）
  dims: [["维度名","说明"],...], // 推荐 · 该类型特有的选型维度
  segs: [...],                // 必填 · 形态分段（见下）
  dead: [...],                // 可选 · 停更警示区/边界物种
  myths: [["误区","真相"],...],// 可选 · 常见误区
  edge: "...",                // 可选 · 与相邻类型的边界一句话
  legal: "...",               // 可选 · 合规位（灰色地带类型必备）
  // ---- 观察区专用（status:"obs" 时）----
  isObs: true,
  obsNote: "为什么还没有推荐",
  obsList: [["项目名","一句话","细分","发现证据"],...]
});
```

`segs`（形态段）结构——**每个形态段必须能写出「默认选谁」，写不出就拆段或放观察区**：

```js
segs: [{
  name: "形态名", tag: "副标签",
  def: { proj: "默认推荐项目", meta: "★ 星数 · 协议 · 活跃度", why: "为什么是它（一句话，要能指导具体的人做具体选择）" },
  risk: "⚠ 该形态的风险提示（可省略）",
  swaps: [{ t:"什么情况下换", p:"换成谁", m:"★ 数据", d:"为什么" }, ...],
  nofit: "这个形态段不适合谁（可省略）"
}]
```

## 内容从哪来（发现漏斗）

项目不做全量爬取。发现流程是四层漏斗（详见 `docs/`）：

```
① 热度雷达（GitHub Trending / HN / V2EX / 掘金，全部带时间戳证据）
② 双圈交叉确认（中英文两个圈子都讨论的才算真热；转载只算一个源）
③ 验证闸门（GitHub 硬数据：push 日期 > star；协议以 LICENSE 文件为准）
④ 类型裁决（写得出「默认选谁」的建类型页；太新的进观察区）
```

沉默但可靠的项目走「采用验证」通道：发行版自带、软件源常青、被写进默认安装步骤。

## 部署到 GitHub Pages

1. 在 GitHub 新建一个仓库（建议名 `oss-nav` 或任意）
2. 把本项目全部文件上传（保持目录结构，`.nojekyll` 也要）
3. 仓库 **Settings → Pages → Build and deployment → Source 选 `Deploy from a branch`**
4. Branch 选 `main`，目录选 `/ (root)`，保存
5. 一两分钟后访问 `https://<用户名>.github.io/<仓库名>/`

以后更新内容：在 GitHub 网页上直接编辑对应的数据文件 → Commit → Pages 自动更新（约 1 分钟）。
