## 类型页成稿

### 是什么

「API token 网关」指：把多家 AI 模型供应商的接口和密钥集中到一个入口统一管理的工具——你的应用只对一个地址、一把 key，背后接哪家模型、怎么分流、谁用了多少，都由网关说了算。【事实·定位综述】

这个类型里的工具分三种完全不同的形态：有的只是你电脑上的一个切换器（不搭服务），有的是自己跑一个轻量转发，有的则是带管理后台、能管人管钱的完整平台。**先分清你要哪一种，比比功能重要得多**——三者装错位，要么大材小用，要么力不从心。【事实·见形态分段】

### 适合谁 / 不适合谁

适合：同时用多家模型服务想统一入口的人（个人或团队）、要给多个应用/成员分发模型访问权限的团队、想监控用量和成本的人。
不适合：**只固定用一两家供应商、从不换 key 的人**——网关是给「多」和「变」准备的，单一供应商直连即可；想靠网关「对外经营转售服务」的——那涉及面向公众提供 AI 服务的资质与备案，本页不提供开业指导【方案 §6.2 合规位】。

### 选型维度表（选网关看这五条）

| 维度 | 说明 |
|---|---|
| 服务对象 | 就你自己 / 一个小团队 / 要开账号给很多人——决定形态段 |
| 凭据类型 | 只有 API key，还是订阅账号（Claude/Codex 那类）也要统一管 |
| 协议转换 | 应用说 OpenAI 方言、上游说 Anthropic/Gemini 方言时，谁来做翻译 |
| 计量与计费 | 只要用量统计，还是要额度、分摊、充值体系 |
| 界面偏好 | 桌面 App / 一个配置文件 / Web 管理后台 |

### 形态分段短名单

#### 段一 · 个人桌面切换器（不搭服务）

**默认选谁：cc-switch**。
理由：同时用 Claude Code、Codex、Gemini CLI 等多个编码工具的人，每个工具配置文件格式不同、换供应商要挨个手改。cc-switch 一键切换 10 个编码工具的供应商配置（改前自动备份）、内置 90+ 供应商预设，还能起本地路由做 API 格式互转和故障转移【事实·README】。146k star（GitHub API 双端点交叉核验）、2026-10 仍在活跃提交【事实·API】。

**什么情况换：** 该形态内暂无体量相当的替代品【待确认·此判断需定期复查扩散搜索结果】。

**不适合谁**：要让多人共用模型资源的——切换器只管你一台电脑，那是网关的活。

**边界一句话**：只是偶尔手动换一两家供应商的，先别装任何工具，改配置文件也就一分钟；切换器的价值从「天天切、切的工具多」开始成立。【待确认·判断句，需人核】

**⚠️ 项目内风险点**：cc-switch 的「订阅账号接入（Beta）」功能，README 自己提示可能违反上游服务条款【事实·README】——用官方 API key 没这个问题，用订阅账号接入需自行评估。

#### 段二 · 个人轻量网关（一个 Docker 容器的事）

**默认选谁：uni-api**。
理由：它的 README 直接写明了存在动机——「one/new-api 对个人太复杂、太多个人用不上的商业功能」【事实·README 原话】。纯配置文件驱动、无前端，但该有的都有：多后端统一成 OpenAI 格式、加权/轮询负载均衡、失败自动冷却、key 级权限与限速【事实·README】。想要「把多家 API 捏成一个本地端点」的最短路径，就是它。

**什么情况换：**
- 主要目的是**零成本试用**各家模型 → **freellmapi**：把 34 家厂商的免费额度聚合成一个 /v1 接口，官方定位就是个人实验工具【事实·README】。
- 想要图形管理界面但仍是个人规模 → 直接看段三的 gpt-load。

**不适合谁**：要给团队开账号、发 key、管权限的——没有用户体系的网关管不了人。

#### 段三 · 团队网关（带管理后台，管人管钱）

**默认选谁：new-api**。
理由：one-api 系里当前生态最活跃的继承者——原版 one-api 最近一次代码提交停在 2026-01，new-api 截至 2026-10-20 当天仍在提交【事实·API】。功能是完整形态：OpenAI/Claude/Gemini 三种原生协议出口、额度与订阅计费、OAuth/2FA 登录、七语言管理后台【事实·README】。

**什么情况换：**
- **单管理员、不想搞多用户**，但想把 API key 和订阅账号（Codex/Claude 等的 OAuth 账号）放进同一个凭据池统一调度 → **gpt-load**：这是它相对 one-api 系最明确的差异点，凭据本地加密、内嵌管理台【事实·README】。
- **团队是 Python 技术栈**，想在代码里（SDK）和网关侧用同一套东西 → **LiteLLM**：pip 装的 SDK 和可部署的网关服务双形态，virtual keys、预算追踪、管理后台齐全【事实·README】。**注意：主体 MIT，但 enterprise/ 目录是单独的商业协议**，GitHub 因此识别为「无标准协议」——商用前必须看清【事实·LICENSE】。
- **国际化团队、要把输入输出防护（guardrails）内置在网关层** → **Portkey gateway**：国际主流开源 AI Gateway，路由 1600+ 模型、50+ guardrails【事实·README】。其部署方式与近期商业变动信息本次未完全核实【数据缺口·引用前需复核】。

**停更警示区**：**one-api**——这个品类的开山之作、中文社区教程最多，但截至 2026-10-20 已约 9 个月无代码提交【事实·API push 2026-01】；**one-hub**（one-api 增强二开）main 分支 2026-02 后同样无提交【事实·commits 页】。旧教程仍多，新部署建议向活跃后继者迁移【待确认·判断句】。

#### 边界物种区（提及但不进短名单，收录与否待裁决 ⚠️）

- **claude-relay-service**：把 Claude/Codex/Gemini 的**订阅账号池化「拼车」共享**。两个硬事实：README 自述此用法可能违反 Anthropic 服务条款；v1.1.248 及之前存在已披露的管理端鉴权绕过漏洞（需升级到 1.1.249+ 或迁移 2.0）【事实·README】。**LLM 裁定：不进短名单**；是否值得作为条目收录展示，提交人裁决【待确认·规范三态中的中间态，首次触发】。

### 常见误区

1. **「star 最多的就是最好的」**——one-api star 37k 依然最高梯队，但代码已停摆 9 个月【事实·API】；本类型的质量第一信号是提交日期，不是 star。
2. **「协议是 MIT 就能随便商用」**——LiteLLM 的 MIT 不覆盖 enterprise/ 目录【事实·LICENSE 文件】；混合协议项目要看清每个部分。
3. **「切换器和网关是一回事」**——切换器改的是你电脑上的配置文件，网关是一个持续运行的服务；前者管「你」、后者管「大家」【事实·形态区分】。
4. **「搭了网关就能对外卖服务」**——面向公众提供 AI 服务涉及资质与备案，这是另一回事，本页只做选型不做出开办指南【方案 §6.2 合规位】。

### 相关类型

- **本地大模型运行**：自己跑的 vLLM/LocalAI 服务的地址，同样可以作为上游接进网关统一调度【事实·网关接任意 OpenAI 兼容上游的通用能力】
- **AI 编程助手**：段一切换器的主要服务对象，二者的关系是「工具」与「工具的配置管家」

## 规范执行标注（复盘素材）

1. **用户拍板的「合并」经受住了检验**：cc-switch（146k star）与 new-api（50k star）同页共存，靠形态分段（切换器/轻网关/团队网关）让两段判断都写到了「默认选谁+什么情况换」的锐利度——grok 的「上下游不可合并」反对被页面结构消化，未出现判断失焦。**此为案例 1 最重要的结论。**
2. **灰色物种三态机制缺口**：claude-relay-service 同时踩中「ToS 风险」与「历史安全漏洞」，既非纯违规类型（不收录清单管不到）也非干净项目——规范 v0.1 只有「收/不收」两态，实际需要第三态「提及但不进短名单」。需补进规范。
3. **祖师爷效应确认**：one-api（37k star）停摆 9 个月 vs new-api 当日提交——「push 日期优先于 star」规则在两个案例中都成为关键判据（GPT4All、one-api 双双验证）。
4. **混合协议是新常态**：LiteLLM（MIT+商业目录）、Jan（API 识别与 README 不一致）——「协议」字段需要支持混合/待核标注，且必须落实到类型页正文（误区 #2）。
5. **ToS 自述风险的传递**：cc-switch 账号接入 Beta、claude-relay-service 整体——README 自标上游 ToS 风险的功能，项目卡与正文均需警示，LLM 不得因「star 高/常用」淡化此风险。
6. **扩散搜索贡献率 45%**：11 个项目中 5 个来自扩散搜索（Portkey/claude-relay-service/freellmapi/one-hub/Squirrel），其中 freellmapi（37.7k）、Portkey（13.2k）为漏收的重要项目——「扩散搜索」作为发现引擎的价值得到量化验证。
7. **数据异常双端点核验成为必需**：cc-switch 146k star 异常偏高，子代理用两个独立 API 端点交叉验证一致后如实记录——采集工序需要把「异常值交叉验证」写入 SOP。
8. **用户体验注入点就绪**：freellmapi 用户本人部署过（WSL/docker，端口 7001）——其亲测体验句按规范属「人写判断栏」，需用户口述后注入，LLM 不代笔。
9. **官方性能自称标注**：LiteLLM「1k RPS 下 P95 延迟 8ms」为 README 自述，未独立核实——与案例 2 的 vLLM「SOTA」同规则：官方自称必须带标注。
