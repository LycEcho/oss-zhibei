# 筛选与总结规范 v0.5

> 本规范管三件事：**找**（从哪里发现项目）、**筛**（决定收录谁、淘汰谁）和**写**（把事实变成有判断的介绍）。
> 它是 LLM 生产内容的工作手册，也是人审的验收标准。随案例迭代，每版记录修订原因。
> 上位依据：`docs/开源选型站产品方案.md`（2026-10-20 定稿）。

## 零、发现规范（开头必须可靠）

> 起点不新鲜，后面全靠扩散补救，漏掉多少新星不可控（用户 2026-10-20 指出，案例验证成立：
> 搜索引擎索引的是过去，star 排序霸屏的是老项目）。

### 0.1 总原则：发现与验证分离

- **新闻/社区讨论负责「发现」**（谁新鲜）——热度只是入池资格，不是收录理由
- **GitHub 硬数据负责「验证」**（活得好不好）——push 日期、发版节奏、issue 响应说了算
- 两者混用（「新闻说它火所以它好」）是发现环节的头号错误

### 0.2 第一层：热度雷达（每周例行）

| 源 | 圈子 | 拿什么 |
|---|---|---|
| GitHub Trending（日/周） | 全球开发者 | 此刻涨得最快的项目 |
| HN（含 Show HN 新品区） | 英文硅谷圈 | 被讨论的新项目 + 发布即雷达 |
| Reddit（按领域选版：r/LocalLLaMA、r/selfhosted…） | 英文兴趣社群 | 真实用户在用什么、怎么称呼这类东西 |
| V2EX / 掘金 / 公众号技术号 | 中文圈 | 中文生态的真实讨论与自然语言称呼 |
| GitHub Daily Radar 类聚合（近 7 天新建+涨星排序） | 全球 | 专抓「新但还没霸屏」的项目 |

- 每源产出两样：**本周被讨论的项目名单** + **讨论里人们对这类东西的自然语言称呼**（用户词表，
  比项目自述词更接近真实搜索意图）
- **单源只是线索，不是证据**（不同圈子热度完全不同）

### 0.3 第二层：锚点扩散

- 从当红项目的 README/description/竞品对比中提取定位词与互相引用，作为搜索种子
- GitHub 关键词搜索**强制按 `created:`（挖新星）/ `pushed:`（查活跃）排序，禁止默认 star 排序**——
  star 是年龄的函数，默认排序等于让死人霸屏
- 扩散结果同样要过第三层闸门，不因「搜出来的」免检

### 0.4 第三层：验证闸门

- 按第一章 1.2 质量信号硬性核查（push 日期为第一信号）
- **交叉确认**：≥2 个独立源提及（新闻/社区/GitHub 活跃数据，任二）才入池；孤证进观察区

### 0.5 僵尸项目与新星的正确去处

- **停更警示区**：过气项目不占推荐名单，但进类型页警示区——搜教程来的人最需要「别用这个，
  它死了」的提醒（案例 2·GPT4All 验证：负面空间是价值点，不是垃圾）
- **新星观察区**：创建 <6 个月但增长快（Trending/Radar 出现）的项目——活跃时长不够，不进短名单，
  页面留痕跟踪，够资历后转正

### 0.6 来源独立性与去重（「双圈交叉」必须是真的）

- **转载/引用环路不算独立确认**：多家媒体转同一篇稿、HN 引博客又引回 HN，都是一次事件的多次放大。
  独立性按**内容血缘**判断（同文转载=1 源），不按站点数量。
- **一手社区不自动可信**：HN/Reddit/V2EX 的软文是营销预算的第一站；作者自己的展示帖是一手但非独立。
- **中英文双圈天然去环**：跨语言同时被讨论是最便宜的独立性证明。
- 旧报道计入独立确认需时间衰减（三年前的不算「当前被讨论」）。

### 0.7 按物类换尺子的采用证据（依赖反查不适用时的补洞）【mimo 决策】

| 工件类型 | 「有人真在用」的尺子 |
|---|---|
| 库/SDK | 被依赖数（警惕传递依赖虚高）、下载量**生态内百分位**、semver 纪律 |
| CLI/开发工具 | Homebrew/apt/nixpkgs 等软件源收录、release 资产下载量、发行版打包维护者存在 |
| 桌面/GUI | 安装包下载量、**翻译覆盖数**（社区愿意做 i18n=真实用户）、issue 里环境多样性 |
| 服务/自托管 | Docker pulls、Helm chart、r/selfhosted 长期讨论、可交叉核验的企业案例 |
| 插件/扩展 | 市场安装量与评分、宿主社区问答量 |

- **通用层（跨类型成立的贵信号）**：issue 首次响应时长、非维护者结案率、**职位要求（JD）提及**
  （公司只为真在用的技术写 JD，最被低估）、以年计的响应记录。
- 人数与公司背书**只作备注、不作否决**：sqlite/curl 皆少数人长扛；公司背书恰是改协议高发区；
  「完成态软件」不活跃是因为做完了——用「是否仍响应安全报告」区分完成与弃养。

### 0.8 沉默可靠通道与双毕业通道【mimo 决策】

- 雷达只看得见「被讨论」的；**沉默可靠通道**专抓「冷静的人已把它当默认」的：发行版自带、
  软件源里躺多年、别人的安装文档把它写成默认步骤、依赖树反查、下载量生态内百分位。
- README 企业 logo 与 awesome 常青成员**降为线索层**（最可伪造/惯性不删），永不作毕业证据。
- **双毕业通道**（缺一则沉默通道是装饰）：
  ① **讨论验证**——≥2 个独立源（按 0.6 去重）讨论；
  ② **采用验证**——0.7 的采用证据矩阵达标（适用于从未被讨论但被大量使用的项目，如 curl 类基建）。
- 任一通道通过才可进短名单；两通道都不过但被提及 → 观察区。

### 0.9 类型页内双线呈现 + 复评降级（不做综合分）【grok 决策】

- **禁止综合分**（把「热」和「稳」搅成一个数字=正确的废话，且是 Goodhart 单点靶）；
  全站也不设「新星区/常青区」两块榜——用户是带着具体任务来的。
- **每个类型页内写两句分开的话**：①「正经拿去用，默认选谁」（可以直说「还没有」）；
  ②「最近冒出来、还没经住时间的，是谁」（观察区新星，不与默认推荐抢同一句话）。
- 品类太新写不出默认选项就照实写——比硬编诚实。
- **展示证据不展示徽章**：每项列出通过/未过哪些信号 + 最后核验日期；信任来自出处。
- **复评 TTL 与降级**：短名单非终身制——改协议、作者弃养、安全公告无人接 → 降级并记录
  （负面知识登记）；所有事实带「最后核验」时间戳，过期自动降级。
- 常青线季审复核，新星线快速复查（更新节奏随线不同）。

## 一、筛选规范

### 1.1 硬性门槛（一条不满足直接淘汰，不进讨论）

| # | 门槛 | 说明 |
|---|---|---|
| 1 | 真开源 | 有明确开源协议。**协议以 LICENSE 文件为准**（案例 2·Jan：GitHub API 识别与 README 自述不一致时标「协议待核」）；**混合协议**（如 LiteLLM 主体 MIT + enterprise/ 目录商业协议）必须逐部分标注，类型页正文要点名（案例 1）；**source-available 协议**（ELv2 等，源码公开但非 OSI 开源，如案例 3·context-mode 31k 星实为 ELv2）按「受限协议」标注，能否进短名单由人裁决。闭源免费工具**默认不收**；若该类型里绕不开（如 LM Studio 之于本地推理），以「对照项」出现并明标「闭源」，不进短名单 |
| 2 | 非 fork/镜像/教程 | awesome 清单本身、翻译搬运、教程仓库一律不收 |
| 3 | 活跃 | 近 6 个月有 commit。例外：停更但仍是事实标准的项目可特批收录，状态标「停更」 |
| 4 | 合法合规 | 不踩「不收录清单」：翻墙代理、机场面板、盗版破解、影视聚合、外挂私服、社工库定位、赌博、水军、绕过付费/版权的下载器、深度伪造 |
| 5 | 归属明确 | 能确认作者/组织，不是来路不明的搬运仓库 |
| 6 | ToS 灰色走三态 | 用法可能违反上游服务条款的（案例 1·claude-relay-service 订阅拼车、cc-switch 账号接入 Beta）不适用「收/不收」两态，走**三态**：①收录进短名单 ②**提及但不进短名单**（正文边界区点名+风险警示）③完全不收录。三态中②③由人裁决，LLM 只起草建议 |

### 1.2 质量信号优先级（判断「值不值得进短名单」）

- **第一梯队（硬信号）**：**最近 push 日期（活跃度第一信号，两案例均验证：GPT4All 17 个月、one-api 9 个月无 push 均靠它抓出）**、包管理器下载量、commit 频度、发版节奏、严重 issue 响应情况、贡献者数、被下游依赖数
- **爆火项目专项**（案例 3·rea 验证）：open issues/PR 积压量必须与 star 一起报告——爆火期 issue 响应比 star 更能说明可用性；媒体引用的星数是**快照**（注明时点），与实抓数据并存，矛盾时先核对时间点再判真伪
- **第二梯队（参考）**：star 数——它只是年龄和热度的函数，**禁止单独作为质量证据**；**star 异常偏高时（如案例 1·cc-switch 146k）必须换独立 API 端点交叉验证后如实记录**
- **README 只回答「它自称是什么」**，不回答「好不好」——禁止拿 README 的语气当质量判断依据

### 1.3 类型与形态归属

- 一个项目可属多个类型，但每个类型页只呈现与该类型相关的面（另一面在该项目卡上注明）
- **形态判定**：属于该类型下的哪个形态段（个人 / 团队 / 生产级…）。跨形态项目（既是库又是服务）按主打形态归段并注明
- 归属拿不准时**标注待确认**，由人拍板——归属错了比漏收更伤

### 1.4 状态与淘汰

- 已归档/停更 → 不进短名单，可进类型页的「已停更」负面区（负面试错也是内容）
- 开源改商业协议 → 必须标注「X 年 X 月改协议」，短名单里要写明影响
- 每个项目卡必带**核验日期**（数据是哪天抓的）；过期判断比没有判断更糟

## 二、总结规范（怎么写）

### 2.1 项目卡固定字段

```
slug / 一句话定位（≤20 字，说清给谁用）/ 类型+形态 / 协议（支持「混合」「待核」标注）/
部署形态（桌面 App / Docker / pip / 二进制…）/ 关键功能（≤5 条）/
活跃信号（近 3-6 个月事实，push 日期优先）/ 状态（活跃/停更/改协议）/
ToS 风险警示（README 自标违反上游条款的功能必须列出）/ 核验日期 / 证据链接
```

### 2.2 类型页结构（七件套 + 形态分段）

1. **是什么**（3 句内，外行能懂）
2. **适合谁 / 不适合谁**（点名具体场景，禁套话）
3. **选型维度表**（该类特有的 3-5 个比较维度）
4. **形态分段短名单**：每段 = 默认选谁 + 最多 3 个「什么情况换」+ 不适合谁。**某段写不出锐利判断 → 拆出去独立成页，宁分勿混**
5. **常见误区**
6. **相关类型**（带边界一句话，如「只是本地切换接口的，不必上整个网关」）
7. **核验戳**（AI 起草 + 人核验日期 + 核验人）

### 2.3 LLM 分工红线（本规范的核心）

| 层级 | 内容 | 规则 |
|---|---|---|
| ✅ LLM 直接写 | 事实：是什么、功能清单、协议、部署方式、活跃数据、对比表 | 数据必须在事实包里有出处 |
| ⚠️ LLM 起草、人确认 | 形态归属、类型命名、默认推荐、「不适合谁」、负面评价 | 草稿必须标「待确认」 |
| 🚫 LLM 禁写（人没给料就不许出现） | 亲测体验句（「我用下来很稳」）、无数据支撑的断言（「社区很活跃」）、灰用途引导 | 出现即返工 |

**语气规则**：允许「被人坑过」的口气，但每个判断句必须二选一：
① 挂证据（数据/出处/日期）；② 标「未亲测，依据是…」。两者都没有的判断句不许上线。

**性能断言规则**（案例 2·vLLM「SOTA」、案例 1·LiteLLM「8ms」验证）：官方自称的性能数据
必须带「自称/官方口径」标注；只有第三方 benchmark 才能写成客观事实。用户亲测数据可标注为亲测。

### 2.4 禁写清单

- 灰用途：翻墙、白嫖资源、绕过付费——一律不写，哪怕 README 里就有
- **正确的废话**：「各有优劣看场景」「都很优秀」——出现即返工（判断句的最低标准是能指导一个具体的人做具体选择）
- 无日期的时间性断言：「最近很火」「目前主流」——必须换成「截至 X 年 X 月…」
- 绝对化：「最强」「必选」——除非证据硬到能扛住项目方来打脸

### 2.5 中文表达

- 项目名保留原文（cc-switch、new-api），通用概念用中文
- 类型名用人话（「API token 网关」而非「LLM Reverse Proxy Management System」）
- 每个类型页第一段必须让**不写代码的人**也能看懂这是干嘛的

## 三、生产流水线（五道工序）

| 工序 | 干什么 | 谁干 | 产出 |
|---|---|---|---|
| 1 采集 | 抓仓库事实（协议/活跃/README 要点），禁编造、标注来源。**SOP**：①「未获取」的字段必须如实传递到成稿，不得用推测填充；②异常值（如超高 star）须换独立端点交叉验证；③协议口径冲突时以 LICENSE 文件为准并标注 | 机器 | 事实包 |
| 2 筛选 | 按第一章给收录/淘汰/降权清单，每条附理由 | 机器起草+人确认 | 收录决策 |
| 3 起草 | 项目卡 + 类型页草稿，判断栏按 §2.3 分层标注 | 机器 | 草稿（带「待确认」标记） |
| 4 人审 | 确认判断、补亲测体验、盖核验戳 | 人 | 正式内容 |
| 5 复盘 | 案例跑完，把规范不够用/被推翻的地方写回本文件 | 人+机器 | 规范新版本 |

## 四、案例实验记录

### 案例 1：API token 网关 ✅（2026-10-20 完成，见 `案例1-API-token-网关.md`）
- **结论**：用户拍板的合并方案经受住检验——cc-switch 与 new-api 同页，形态分段（切换器/轻网关/团队网关）让各段判断都写到锐利度，grok 的「上下游不可合并」反对被页面结构消化。
- 触发规范修订：ToS 灰色三态（#6 门槛）、混合协议标注、push 日期优先、star 异常核验、ToS 风险警示字段、采集 SOP。
- 扩散搜索贡献率 45%（11 个项目中 5 个来自扩散）——发现引擎价值量化确认。

### 案例 2：本地大模型运行 ✅（2026-10-20 完成，见 `案例2-本地大模型运行.md`）
- **结论**：形态分段跨类型通用（桌面/开发者服务/生产服务器三段均锐利）；「停更警示区」（GPT4All）与「闭源对照项」（LM Studio）机制运作正常，负面空间建立信任的假设获得支撑。
- 触发规范修订：协议以 LICENSE 文件为准、官方自称性能标注。
