# 开源选型站 · 产品方案（定稿）

> 产出方式：kscc 扩散/辩证 → grok-4.7 三轮辩证攻击 → mimo 独立复核 → kscc 汇总定稿。
> 各方观点标注：【grok】【mimo】【kscc】；对定稿起决定性作用的结论标【grok 决策】【mimo 决策】。
> 日期：2026-10-20

---

## 1. 产品定位（一段话）

**一个只做科技领域、靠「人工判断 + 机器供料」维护的中文开源选型站。**
唯一的内容形态是「类型页」：这个类型的工具是什么、怎么选、短名单、不适合谁；类型之下可按
**形态/场景分段**（如网关类型下的「个人切换工具 / 团队网关」），每段各有短名单与判断。
类型按「一次选型决策里会放在一起比的那一组」来切；机器只负责供证据、刷新事实、提名候选，
**判断永远由人写、人背书**。

用户的原始洞察「先理解类型、再下钻项目」被保留，但页面性质从中立百科改造为**带判断的决策页**（见 §3）。

---

## 2. 三条生死判断（为什么必须这样做才活得下来）

### 2.1 主矛盾：覆盖面 vs 判断力【grok 决策，mimo 同构收敛】

- grok 表述：越想自动铺满所有类型，每一页就越像一段谁都能生成的话。人要的不是一张更全的地图，是一份有人维护的意见。
- mimo 表述：可信的向导（判断密集、慢、有限覆盖） vs 规模化的索引（自动化、全品类）。产品宣称的价值恰恰要求前者。
- **推论**：全自动大而全目录是死路；判断力是唯一能区分自己的东西，一切设计为保护判断力让路。

### 2.2 「AI 生成介绍」不是壁垒，溯源才是【mimo 决策】

- 2026 年 LLM 生成百科条目是零门槛动作，内容农场两天复刻。真正稀缺的是：
  持续维护、可核验的事实数据（活没活着 / 许可变没变 / 最近发版）+ 带证据的判断 + 稳定的生态地图。
- **溯源即信任**：每页署名「谁核验的、什么时候核验的、依据什么」，比文笔值钱十倍。
- 负面空间（已废弃 / 改许可 / 被商业化收编 / 不推荐原因）是全网没人做好、建立信任最快的差异化。【mimo 决策】

### 2.3 分发是生死维度，不是上线后的事【mimo 决策】

- SEO 路径在坍塌（AI 内容批量页被搜索降权、用户迁向 AI 助手）；「这是什么」类查询正被 AI 摘要直接吃掉。【grok】
- 策略反转：**被 AI 引用、成为 AI 的数据源 > 抢关键词排名**；首发靠社区渠道（见 §7）。
- 不回答「流量从哪来」的导航站方案是残缺的。

## 3. 产品形态：决策页（用户「标签先行」构想的落地形态）

### 3.1 信息架构

- 用户原始构想「进站先看到类型介绍，再下钻项目」被保留，但修正为【mimo 决策】：
  **类型页 = 决策页，同一页内直接放 Top 项目卡**——介绍是心智解释，项目列表是同页 payload，
  **不设第二跳**（第二跳会导致「浏览成环、到不了项目」，转化数据差还误导决策）。
- 搜索框直达**项目卡**，不是搜标签。落地即可试用/收藏/跳 GitHub。
- 高意图用户走搜索直达；闲逛用户走类型页网络。两条路径并存但页面重心明确服务于「带着任务来的人」。【grok】

### 3.2 决策页七件套（融合 grok 四块 + mimo 决策页模板）

1. **是什么**（3 句以内）
2. **适合谁 / 不适合谁**（点名具体场景与具体坏事，不写套话）【grok】
3. **选型维度表**（3-5 个该类特有的比较维度，如网关看路由/额度/审计）
4. **短名单**（默认选谁 + 最多 3 个「什么情况下换」；其余项目进证据区不进正文）【grok】
5. **常见误区**
6. **相关类型**（类型间跳转，带边界说明，如「只是个人改本地接口的，不必上整个网关」）【grok】
7. **核验戳**：本页由 AI 起草、人工核验于 X 日、核验人 + 每条判断挂日期与出处【mimo 决策】

> grok 补充的粒度约束（按形态段计）：每个形态段的短名单不应是 8-15 个的货架——
> 应该是「一个默认选项 + 最多三个什么情况换」，其余放进证据区。页面才像「意见」而不是「货架」。
> 类型页含多个形态段时，总项目数可以多，但**每段内部必须保持这个密度**。

## 4. 类型体系

### 4.1 分类总原则：多面分类，用途主导航【mimo 决策】

- 「按语言分类过时」是伪命题：**找库（写代码用依赖）时语言是硬约束**，npm/PyPI 按语言组织是对的；
  **找工具（自托管/替代 SaaS）时语言无关**，按用途才对。【grok + mimo 一致】
- 正确模型：**用途 = 主导航；语言 / 许可证 / 部署形态 / 成熟度 = 过滤面（facet）**。
- MVP 只做成品工具，不做库。【grok 决策】

### 4.2 类型切分判据【grok 决策】

> 按「一次选型决策里会放在一起比的那一组」来切。写不出「默认选谁、什么情况换、不适合谁」的类型，不进前 10 页。

科技域第一层示例（grok 给出）：自建多模型网关、向量库、日志监控链路、登录与单点登录、对象存储、
消息队列、管理后台框架、流程审批、全文搜索、团队知识库。

### 4.3 「上升合并」机制（用户原始构想的修正版）

用户的直觉：cc-switch 与 newapi 这类「定位不同但本质是同一类」的项目应合并上升到共同类型，但上升有天花板。修正后：

**合并判据【grok 决策】**：
- 合并看「**同一次决定里会不会二选一**」，且「**短名单能用同一把尺子量**」。两条都满足才可合并。
- 上界：合并后还能写出锐利的选型判断（不是「看场景」这种正确的废话）就还有上升空间；
  只能写出「这是一类后台软件」即到天花板。

**✅ 已拍板（用户裁决，2026-10-20）：合并为一类。**

- cc-switch 与 new-api 合并为同一个类型页，类型名定为「**API token 网关**」。
- 页面结构按用户方案：**类型页内按「形态」分层介绍**——比如「个人本地切换工具 / 团队自建网关 /
  企业级多租户网关」各成一个形态段，**每个形态段各有自己的短名单与选型判断**（个人场景默认选谁、
  团队场景默认选谁）。
- 这个结构同时消化了 grok 的反对：他担心的「两种人的选择写不清」，靠**形态分段各自写判断**解决，
  而不是靠一个混在一起的短名单硬答。
- **设计硬约束（吸收 grok 警告后的让步条件）**：一个类型页内的每个形态段，必须各自能写出
  「默认选谁 + 什么情况换」；若某形态段写不出锐利判断，就把该形态拆出去独立成页，宁分勿混。
- 此裁决确立了类型体系的通用结构：**类型页 = 选型故事 + 分形态短名单**（呼应「介绍这个类型下
  有多少种项目」的原始构想）；与 mimo 的关系模型兼容（形态之间是不同场景的 alternative，子类型是 is-a）。
- 合并流程【grok 决策，保留】：
- **永不自动合并**。机器可提合并提案（附证据），人点头才生效；超时不自动合并、保持分开；队列满了丢新提案。
- 对称机制：类型过大可拆分，同样人点头才动，默认不动。
- 前 10 页不需要这套机制——写到真撞车了再人工并。【grok】
- 工程前提【mimo】：标签 ID 与 slug 分离 + 301 映射表 + 版本化；归并用「映射」不用「删除」
  （合并是不可逆破坏性操作，做错会丢区分度、废已发链接）。

### 4.4 行业维度（✅ 已拍板：做成独立入口，落地为「导流合集页」）

用户拍板：**行业做成独立入口**（一级导航里有行业的位置）。落地时吸收 grok 的警告（行业×类型
交叉矩阵会爆炸、行业页每页都浅），具体约束：

- **行业入口页是「导流合集」，不写选型判断**：一个行业页 = 该行业常用类型页的索引清单 + 每类
  一句人话导引（「做 XX 的通常先碰到这几类」）+ 行业特有的注意事项。判断仍在类型页里，行业页
  只负责把人送对地方。
- 这个结构成本可控（一个行业页就是一份精心编排的清单），也不会稀释类型页的判断密度；
  后期可由 AI 起草、人审发布，与整体人机分工一致。
- **MVP 阶段只放一个「科技」总入口**占位（甚至先静态一页），行业入口的扩展放在 10 个类型页
  验证通过之后——行业入口多了也一样会有「每页都浅」的问题，扩一个行业就要养一个行业。
- 「只做科技行业」仍为主题域红线（用户需求 3），政治/法律高风险行业永久不进。【grok 决策，保留】
- 找依赖的开发者不能丢：语言等作为过滤面保留。【mimo】

## 5. 内容生产与保鲜（人机分工）

### 5.1 分工总则【grok 决策，mimo 同构】

- **机器只许写事实**：协议、最近是否更新、严重 issue 是否有人应答、安装方式、活跃信号。
  **判断栏机器不许填，空着就发不出去**——用「做不到的门槛」防退化，不靠自觉。
- 判断栏必须是人写的三样：默认选谁 / 不适合谁（点名具体人和事）/ 一条亲自核实过（或标明「没亲手用过」附来源）的依据。
- 草稿只留证据包；写好的判断稿超两周删掉，不存着以后补（防忙时成批发旧稿）。
- **人审后合入，永不自动发布**。【mimo 决策】

### 5.2 判断的证据来源【grok】

- issue / Reddit / HN 讨论只当**证据**不当**结论**（沉默的满意用户不发言，汇总会系统性看低无聊但稳的项目）。
- 机器每月交一包证据：近期发布、没人理的严重问题、几条带日期的「我们从甲换到乙，因为丙」。
- 人一个晚上读完、写三句话。**一个晚上写不完的类型，不是现在该做的类型**。
- 可持续性不靠全用过：靠每条判断挂日期与出处、写明没亲手用过、错了就改并留「上次错在哪」。
- 社区投票不做——那是换皮人气榜，与「敢不敢用」相反。【grok + mimo 一致】

### 5.3 保鲜与状态机【mimo 决策】

- 项目状态机：活跃 / 维护中 / 归档 / 死亡 / 商业化改许可。
- 质量信号用：包管理器下载量、commit 频度、发版节奏、issue 响应、贡献者数、下游依赖数；
  **star 只是年龄与 hype 的函数，不单独作为质量信号**。【mimo】
- 季度重验 + 变更订阅（watch 许可/归档事件）；**过期判断比没有更糟**（口气还很确定）【grok】。
- 数据信号优先级：description / topics / 项目名 / 官网 > README 全文（README 只摘要引用、不全文搬运）【mimo】。

### 5.4 用户原始「自动化管线 + 扩散搜索」的最终安放（第二阶段）

管线不是砍掉，是**降级为策展人的放大器**【grok + mimo 共识，kscc 综合】：
- LLM 只做两件事：①「候选提名」——关键词扩散搜索发现新项目/新类型/同类竞品，进人工队列（这就是用户「扩散搜索」的安放）；
  ② 起草介绍稿供人审。
- 每周拉活动度刷新排序与状态。
- 扩散必须有：实体解析去重（fork/镜像/教程/awesome 清单剔除）、负向过滤、停机判据，否则语料单调恶化。【mimo 决策】
- 200 条人工标注评测集 + 一份《分类与收录规范》——这两样才是可复用资产。【mimo 决策】

## 6. 合规红线（用户需求 3 的落地）

### 6.1 不收录类型清单【grok 决策】

常见用途即违规/侵权的，**整类不做**，不靠事后改措辞：
翻墙与代理、机场面板、盗版破解、影视网盘聚合、外挂私服、社工库与定位、赌博、水军批量注册、
绕过付费或版权的下载器。深度伪造宁可不做。

### 6.2 灰色地带类型的写法【grok 决策】

new-api / one-api 这类：**可以收录，但类型名叫「自建多模型网关」**，只讲已有自己账号的团队
怎么管路由和额度。不写：国内访问国外模型、中转怎么赚钱、稳不稳定、免翻墙。
页上留一句：「这是选型，不是开业指导；面向公众提供服务需自行满足生成式 AI、备案、数据出境要求。」
——若不写灰用途就写不出「默认选谁」，这一类先不进前 10 页。

### 6.3 防线层级

主防线 = 不收录清单 + 人写判断时的**禁写清单**；关键词过滤只是最后一道兜底。【grok】

### 6.4 法务补充【mimo】

GitHub API/ToS 合规、商标使用、AI 生成内容标注义务、国内备案与托管、隐私（搜索查询可能含敏感意图，日志留存策略）。

## 7. MVP（4 周，成本近乎为零）

### 7.1 不做什么【mimo 决策】

全量爬取、关键词扩散循环、自动归并、全品类、用户账号、站内纠错按钮、长篇 AI 百科、任何商业化。

### 7.2 做什么

1. **首发垂直领域（✅ 已定）：AI 工程基础设施**（API token 网关、观测/评估、agent 框架、
   本地模型部署等）。
   依据：用户拍板「科技相关的都可以」，按 grok「前十页必须是有疤的领域」原则代选——
   用户亲手部署调试过 LLM API 聚合代理、langfuse（观测）、Dify（应用平台）等，这一域的「疤」
   最真实；且用户举的例子（cc-switch、newapi）全部在此域，兴趣与素材天然集中。
   垂直里做第一，好过全品类里做倒数第一。【mimo】
2. **数据即代码库**【mimo 决策】：一个 Git 仓库——
   `taxonomy.yaml`（类型定义、同义词、父类型、收录标准、选型维度）+
   `projects/<slug>.yaml`（仓库地址、一句话定位、类型、形态、许可、部署方式、活动信号、核验日期、状态）。
   **PR 就是纠错按钮，git 历史就是溯源，版本控制解决标签改名。**
3. 站点由仓库生成：**30-50 个类型 × 每类 10-30 个项目**，人手可及、每条可核。类型页 = 决策页（同页 Top 项目卡）。
4. 搜索直达项目卡。
5. 管线只做两件事：每周拉活动度刷新排序；LLM 候选提名 + 起草。**人审后合入，永不自动发布。**
6. 200 条人工标注评测集 + 《分类与收录规范》。
7. 反馈走 Issue / 社群（用户在哪就去哪），不做站内表单。
8. **分发先行**：掘金/HelloGitHub 投稿、V2EX/即刻、公众号，与 awesome 列表互链。【mimo 决策】

### 7.3 验证假设（一句话、可证伪、有 kill 判据）【mimo 决策】

> **假设**：中文开发者在挑选某一类开源工具时，需要一张持续维护、带选型维度的类型地图，
> 愿意从这里进入决策流程（而不是只看 awesome、或只问 LLM）。

- 4 周：人肉做 **10 个决策页** + 1 个落地页，同页模板 A/B 两版（介绍在上 vs 列表在上——直接实证「第二跳」争议）。
- 投 3 个渠道，测：类型页→点击项目/跳 GitHub/收藏的**完成率**、**回访率**（第 2/4 周）、
  **站内搜索零结果率**、收藏/订阅增长。
- grok 的补充指标：有没有人说「这页告诉了我问 AI 得不到的东西」。

**Kill 判据**【mimo 决策】：
- 列表在上的版本完成率不输甚至赢介绍在上 → 砍介绍重资产，只做数据与榜单；
- 无自然回访、无收藏、无社群增长 → 用户只要「一次性答案」（LLM 已满足），**停止做站**，
  转向做结构化数据集/API 供他人消费；
- 搜索零结果率高但查询集中在 3-5 个词 → 那就是下一步的类型路线图（**查询日志是产品指南针**）。

## 8. 扩张路径与断点预警

- **路径不是 10→100→1000**：十页有人回访之后，先把这十页**改到会过期、会认错**，再加第十一页。【grok 决策】
- **断点一（第 11-30 页）**：没踩过坑的类型一上来，口气从「被人坑过」变成「读过简介」，转发先停。【grok】
- **断点二（几十页的维护）**：一个人季审不了八十页；此时该停更并复审，不该继续加页。【grok】
- 一百页会逼你降门槛或找人；一找人，「一个人的口味」就变回目录。一千页不是放大版，是另一种产品。【grok】
- **成功的死法**：搜索流量涨了，判断没了。【grok】
